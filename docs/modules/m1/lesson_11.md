## Місце в алгоритмічній трійці

Другий із трьох практикумів (позиції 8/11/16), що складають одну навчальну дугу, не три випадкові набори задач:

```
              ALGORITHMIC THINKING
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       П1            П2          П3
    EVALUATE        CHOOSE     REPRESENT
   complexity      strategy    data structure
       │              │            │
       └──────────────┼────────────┘
                      ▼
             TRADE-OFF THINKING
```

```
П1 — EVALUATE: «Наскільки дороге моє рішення?»
        ↓
П2 — CHOOSE: «Яку властивість даних я можу використати?»
        ↓
П3 — REPRESENT: «Чи можу я змінити представлення даних, щоб отримати кращий алгоритм?»
```

П1 навчив рахувати ціну рішення (коректність ≠ ефективність). П2 йде далі: **«Можу просто перебрати все» → «А чи знаю я щось про дані, що дозволить зробити краще?»**

**2 години, усі чотири стратегії, нерівна глибина** — це свідоме рішення, а не недогляд: лінійний пошук студент фактично вже вміє писати, тож він отримує найменше часу; бінарний пошук — короткий guided-приклад; два вказівники і sliding window — дві основні практики уроку.

## CONCEPT — чотири стратегії, кожна під свою властивість даних

```
UNSORTED          → linear scan          O(n)
SORTED            → binary search        O(log n)
                   | two pointers        O(n)
CONTIGUOUS RANGE   → sliding window       O(n)
```

### 1. UNSORTED → лінійний пошук (коротко)

Якщо про порядок нічого не відомо — єдиний надійний спосіб перевірити кожен елемент по черзі. `O(n)` — базовий рівень, з яким порівнюється все далі.

### 2. SORTED → бінарний пошук

Відсортовані дані дозволяють відкинути половину списку за одне порівняння із середнім елементом. **PREDICT перед RUN:** скільки порівнянь потрібно для `n = 1000` і скільки для `n = 2000`? Реальний підрахунок (не оцінка на око, а лічильник у коді) показує: подвоєння `n` додає лише **одне** додаткове порівняння — це і є сенс `O(log n)`.

### 3. SORTED → два вказівники (основна практика)

Класична задача **Two Sum**: `numbers = [1, 2, 4, 7, 11, 15]`, `target = 9`. Два вказівники — `left` з початку, `right` з кінця:

- сума замала → `left += 1` (наступне число зліва точно більше);
- сума завелика → `right -= 1` (наступне число справа точно менше);
- сума збіглась → знайдено.

Кожен крок відкидає рівно одну можливість, а не одну пару — звідси `O(n)` замість перевірки всіх `C(n, 2)` пар. У конспекті це підтверджено прямим порівнянням кількості кроків двох вказівників проти кількості перевірок наївного повного перебору на тих самих даних.

**Це працює тільки тому, що дані відсортовані** — зсув вказівника монотонно змінює суму лише за умови порядку.

### 4. CONTIGUOUS RANGE → sliding window (друга основна практика)

Задача: максимальна сума суцільного відрізка фіксованої довжини `k`. Наївний спосіб перераховує суму вікна заново на кожному кроці — `O(n·k)`. Сусідні вікна відрізняються лише двома елементами (один випадає зліва, один додається справа), тож суму можна оновлювати, а не рахувати заново — `O(n)`:

```python
window_sum += numbers[i] - numbers[i - k]
```

## TRANSFER

Структурно ідентична задача з іншою поверхневою деталлю: та сама техніка ковзного вікна, але шукаємо **мінімальну** суму відрізка замість максимальної — `max`/`min` міняються місцями, решта коду та сама.

### Two Sum ще не закінчився

Той самий `target = 9` повертається в Практикумі П3 (позиція 16), але вже з **невідсортованими** даними `[11, 2, 15, 7, 1, 4]`. Це не випадкове дублювання — designed recurrence: два вказівники напряму більше не працюють (сортування коштує), і на заміну приходить `dict`/`set`-підхід. Один і той самий принцип наскрізь через М1: **алгоритм залежить не тільки від задачі, а й від представлення даних.**
