## CONCEPT — навіщо існують модулі, і що робить `import`

Будь-який `.py`-файл — це модуль, окремий **простір імен**. Дві функції з однаковою назвою в різних модулях не конфліктують, бо звертання завжди йде через ім'я модуля (`xml_reader.parse(...)` vs `json_reader.parse(...)`).

**`__name__ == "__main__"`** — Python встановлює `__name__` у `'__main__'`, тільки коли файл запущено напряму; при `import` він дорівнює назві модуля. Тому код усередині `if __name__ == "__main__":` виконується лише при прямому запуску файлу, а не коли його імпортують.

**Що відбувається при `import math`:**

```text
1. SEARCH   — шукаємо math за sys.path
2. COMPILE  — компілюємо в байткод
3. EXECUTE  — виконуємо файл модуля зверху вниз
4. CACHE    — зберігаємо в sys.modules['math']
```

Повторний `import math` **не** виконує файл ще раз — бере вже готовий об'єкт із `sys.modules`. Звідси випливає небезпека **shadowing**: якщо назвати свій файл `random.py`, Python знайде його раніше за стандартний модуль (пошук іде по `sys.path` починаючи з поточної папки) — і `import random` підвантажить не той код.

**Три стилі імпорту:**

| Стиль | Синтаксис | Коли |
|---|---|---|
| Модуль цілком | `import math` | багато функцій, потрібна ясність (`math.pi`) |
| Конкретні імена | `from math import pi, sqrt` | кілька функцій, часто використовуються |
| З псевдонімом | `from math import pi as PI` | довгі назви, уникнення конфліктів |

`from math import *` (wildcard) не використовуємо — забруднює простір імен, незрозуміло звідки взялось ім'я.

**Правило:** перед тим як шукати пакет на PyPI — перевір, чи немає потрібного в стандартній бібліотеці (`datetime`, `calendar`, `collections`, `re`, `json`, `math`, `os`...).

## CREATE — `datetime`, `calendar`, `Counter`, `locale` на реальних даних

Сценарій: ресторан веде записи замовлень із мітками часу (`timestamp`). Власнику потрібна аналітика по роках, місяцях, днях тижня, годинах.

1. **`datetime`** — дата й час одним об'єктом: `dt.year`, `.month`, `.day`, `.hour`, `.weekday()`.
2. **`strftime`** — datetime у рядок: `%Y-%m-%d`, `%A`/`%a` день тижня, `%B`/`%b` місяць.
3. **Порівняння** — `datetime` порівнюються як числа (`<`, `>`, `==`), звідси перевірка «чи дата в проміжку»: `start <= dt <= end`.
4. **Дані** — 2000 синтетичних замовлень за 2023–2024 роки з випадковим `timestamp` (`random.seed(42)`).
5. **`.dt` аксесор pandas** — той самий атрибут `datetime`, застосований одразу до цілої колонки: `df["timestamp"].dt.year`.
6. **Фільтрація** — по року, по місяцю, комбінована через `&`/`|`/`~` (кожна умова в дужках — інакше пріоритет операторів ламає вираз).
7. **`calendar`** — назви місяців/днів без `pip install`: `calendar.month_name[7]`. **Пастка:** нумерація з 1, `month_name[0] == ""`.
8. **`Counter` (з `collections`)** — підрахунок входжень компактніше за ручний `d.get(key, 0) + 1` з Уроку 6, коли треба саме порахувати частоту: `Counter(список).most_common(3)`.
9. **Похідні колонки** — рахуємо `year`/`month`/`weekday`/`hour`/`meal` один раз, фільтруємо потім скільки завгодно разів.
10. **`locale`** — назви місяців/днів іншою мовою. **Обов'язково `try/except`**: доступні локалі залежать від конкретної машини (ОС, встановлені пакети) — код, що працює на комп'ютері викладача, може впасти на іншому лише через відсутність локалі, хоча логіка правильна. Немає локалі → чесний відкат до англійських назв, без падіння.
11. **Класифікація на межах діапазонів** — `meal_type_from_hour(hour)` і `day_from_timestamp(ts)`: стандартний модуль тут не самоціль, а джерело для бізнес-рішення. Перевірено асертами саме на межах (`11`, `15`, `16`, `17`, `23`) — там ховаються помилки «на одиницю».
