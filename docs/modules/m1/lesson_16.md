## RETRIEVE

Без підглядання: що робить `counts[char] = counts.get(char, 0) + 1` і навіщо саме `.get(key, 0)`; яку пару значень знайшов two-pointer розв'язок П2 на `numbers = [1, 2, 4, 7, 11, 15]`, `target = 9`; чому two-pointer вимагає відсортованих даних.

## CONCEPT + CREATE — Two Sum на невідсортованих даних

Той самий `target = 9`, ті самі значення, але тепер `numbers = [11, 2, 15, 7, 1, 4]` — **навмисне повторення** Two Sum із П2 (зафіксовано рішенням викладача: sorted → unsorted contrast, щоб майбутній аудит не сприйняв це як випадкове дублювання).

**Спроба 1 — той самий two-pointer, напряму:**

```python
def two_pointer_two_sum(nums, target):
    left, right = 0, len(nums) - 1
    while left < right:
        s = nums[left] + nums[right]
        if s == target:
            return left, right
        elif s < target:
            left += 1
        else:
            right -= 1
    return None

two_pointer_two_sum([11, 2, 15, 7, 1, 4], 9)  # None
```

Повертає `None` — не тому що пари немає (`2 + 7 = 9`), а тому що `numbers[0] = 11` вже більше за `target`: алгоритм лише зменшує правий вказівник і ніколи не доходить до правильної пари. Монотонність, на яку покладається two-pointer, тут відсутня.

**Спроба 2 — відсортувати спочатку.** Working, але значення `2` і `7` знайдені **в позиціях відсортованого масиву**, не в оригінальних індексах `numbers` — довелось би окремо шукати `numbers.index(...)` для кожного. Ціна: сортування O(n log n) + відновлення індексів.

**Спроба 3 — змінити представлення: пам'ятати побачене.**

```python
def two_sum_hash(nums, target):
    seen = {}
    for i, num in enumerate(nums):
        complement = target - num
        if complement in seen:      # O(1) в середньому
            return seen[complement], i
        seen[num] = i
    return None

two_sum_hash([11, 2, 15, 7, 1, 4], 9)  # (1, 3) -> numbers[1]=2, numbers[3]=7
```

Один прохід, оригінальні індекси одразу, сортування не знадобилось.

### Чому `dict`/`set` майже миттєві

`list` перевіряє належність лінійно (O(n)) — порівнює з кожним елементом по черзі. `dict`/`set` обчислюють хеш від значення й одразу переходять у потрібний «кошик» — стала (в середньому) кількість кроків незалежно від розміру (O(1)). Глибина навмисно обмежена цим — без CPython internals, без колізій (це інструкторська теорія `lesson_25_search_hashing`, не матеріал практикуму). У конспекті різниця підтверджена реальним заміром: на 50 000 елементів `set` швидший за `list` у ~7700 разів.

**Головний висновок:** алгоритм залежить не лише від задачі, а й від представлення та властивостей даних — пряме застосування центральної моделі курсу (дані → перетворення → організація логіки).

## CREATE — той самий принцип, ще двічі

**Частотний аналіз:** `has_duplicates` (перевірка дубліката через `set`, O(1) на елемент) і `most_frequent` (Counting-патерн з уроку 6 + `max(..., key=...)`) — обидва верифіковані на порожньому вході, унікальних значеннях і повторах.

**Анаграми:** порівняння частотних словників символів (`is_anagram`, регістрозалежно) замість сортування рядків (`sorted(a) == sorted(b)`) — той самий результат, але O(n) проти O(n log n).
